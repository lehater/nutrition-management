# Nutrition Management — System Overview

> Generated projection from accepted canonical project knowledge. Do not edit this file as a source of truth.

## Product boundary

The system derives household nutrition targets from explicit member/profile inputs and versioned nutrition standards, combines them with normalized food knowledge and executable market offers, then computes one primary 30-day purchase plan. When the purchasable catalog cannot close mapped nutrient gaps, theoretical Base Foods may be suggested separately.

The optimizer must preserve unsupported/unknown evidence rather than claiming false coverage. Purchased package quantity and planned utilized quantity are distinct; unavoidable package surplus affects cost but not planned nutrition.

Canonical source: `docs/requirements/product-requirements.md`.

## System shape

The MVP is one local modular-monolith process backed by one transactional relational database. Four context-aligned modules preserve semantic ownership:

1. Nutrition Targeting — household/member state, nutrition standards and target derivation.
2. Food Knowledge — Base Foods, nutrients, provenance and categories.
3. Market Catalog — SKUs, edible package quantities, merchants, fulfilment channels and offers.
4. Purchase Planning — coherent input capture, optimization, invariant validation and returned plan composition.

No bounded context is a network service. Consumers do not read or write another context's persistence model.

Canonical sources: `docs/architecture/target-architecture.md`, `docs/domain/strategic-model.md`, `docs/domain/context-map.md`.

## Primary planning flow

A planning request establishes an explicit derivation date and market `as_of` instant. Provider data is captured inside one coherent database read scope into an immutable Planning Input Snapshot. The read scope closes before optimization. Purchase Planning builds and solves the accepted deterministic optimization policy, independently recalculates reportable facts, optionally asks Food Knowledge for theoretical gap suggestions, and returns a primary plan or an accepted domain outcome.

Technical solver/import/database failure is never represented as a valid domain `partial` or `no_executable_plan` result.

Canonical sources: `docs/architecture/target-architecture.md`, `docs/application/application-design.md`.

## External interface

The first interface is a deterministic CLI. It requires explicit database path, household identity, derivation date and market-as-of instant and emits canonical JSON. There is no HTTP API, browser UI, authentication subsystem or remote transport in the accepted first slice.

Canonical source: `docs/interface/cli-contract.md`.
